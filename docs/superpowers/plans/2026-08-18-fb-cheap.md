## Item 1 — stale-instance `setTextContent` audit

### Outcome

### Mechanics established first (probe + source, Lexical 0.43)

The hazard: `TextNode.setTextContent` short-circuits on `this.__text === text` against the
**captured** instance's field, before `getWritable()`. A reference held across a cloning TEXT
mutation of the same node therefore silently no-ops exactly when the written value equals the
pre-clone text. `getTextContent()` resolves `getLatest()`, so a
`if (getTextContent() !== x) setTextContent(x)` guard is anti-protective for a stale receiver.

Facts that bound where the hazard can occur (pinned in `setTextContentStaleReference.test.ts`):

1. **Structural clones copy `__text`.** Sibling insert/remove/splice clone a node only for
   linked-list pointer surgery; a receiver made identity-stale by structure-only mutation still
   compares text correctly. Only an intervening TEXT mutation through another reference arms the
   no-op.
2. **Transform receivers are identity-stable.** Every route that dirties a text node in 0.43 also
   clones it (`removeFromParent` and `ElementNode.splice` call `getWritable()` on the affected
   neighbors; there is no mark-dirty-without-clone route left — `internalMarkSiblingsAsDirty`
   survives only inside `splitText`, whose splice clones the same nodes). So
   `$applyAllTransforms`'s `nodeMap.get(key)` hands transforms the instance that stays THE live
   instance through `$normalizeTextNode` and the whole transform array. Verified empirically: in
   the engineered forward-merge scenario (dirty the target via sibling surgery, then append a
   mergeable stray) the transform observed `getLatest() === node` on every call.
3. **Hypothetical staleness in the pipeline would self-heal anyway.** `getWritable()`
   unconditionally re-marks the node dirty; the clone that would make a handed reference stale
   also schedules a re-run, which re-fetches fresh and lands the enforcement write at commit.

Consequence: the only live hazard class is the one the split-and-stack fix addressed — an update
body (or cross-update closure) holding a reference captured BEFORE the node's first text mutation
of the cycle, with the same node text-mutated through a different reference before the held write.

### Refuted findings

A predecessor-spawned audit child reported three RISKY sites, all resting on the claim that
`$applyAllTransforms` hands transforms a stale object after `$normalizeTextNode` forward-merges.
That mechanism is impossible in 0.43 (facts 2 and 3 above; probe evidence). Site-by-site:

- `CursorHandler/core/utils/index.ts:29` (`$removeCursorPlaceholder`) — SAFE. Every caller
  (removalHandlers:39/68/99, insertionHandlers:97/111, `EmptyVerseCaretGuardPlugin.tsx:150`)
  guards on the placeholder being IN the captured instance's text before calling, so the written
  value (text minus ZWSP) always differs from the captured `__text` and the short-circuit cannot
  fire; the write goes through `getWritable()` → `getLatest()` and lands. The update-listener
  caller additionally skips any commit with dirty nodes, so its prev-state reference is
  identity-stable. `editorUpdate` is a synchronous `editor.update` wrapper — no deferral window.
- `NoteNodePlugin.tsx:238` (`$noteTextNodeTransform` NBSP reset) — SAFE, transform-arg
  identity-stable.
- `markerEditTier1.utils.ts:584` (`$noteCallerTextTransform`) — SAFE, transform-arg
  identity-stable through the `$textNodeTier2Transform` call tree.

No legitimately red pin exists for any of the three (the failure is unreachable), so per strict
red-green none received a `getLatest()` change; this section is the documented impossibility note.
