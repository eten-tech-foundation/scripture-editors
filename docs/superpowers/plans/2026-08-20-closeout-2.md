## 1. The phantom `\p` — architectural, not another instance

**Reported.** Type `\qt-s\*` at a paragraph end; change the `-` to a `1`; it settles to a `\qt1s\*`
unmatched pair on a NEW line. Change the `1` back to a `-`, and an erroneous `\p` appears before it
instead of the milestone folding back into the paragraph above.

**Reproduced verbatim**, all six steps. The owner's read — "this keeps happening, I suspect an
architectural issue" — is correct, and the mechanism is one line.

`$unknownSplitRejoinScope` (`markerEdit/markerEditTier1.utils.ts`) dissolves an unknown-split
artifact when the edited leading glyph's bytes stop naming a block marker. Its gate,
`openerBytesEndTheSplit`, asks:

```ts
return getMarkerFn(name.replace(/^\+/, ""))?.type === MarkerType.Character;
```

That is **an enumeration of one marker kind standing in for a property**. The property the rejoin
actually needs is *"these bytes no longer name a BLOCK marker, so the fabricated paragraph has no
reason to exist"*. Measured kinds: `nd`/`w` are `Character`, `qt-s`/`qt1-s`/`ts-s` are `Milestone`,
`f` is `Note`, `p`/`q1` are `Paragraph`, `qt1s` is `undefined`.

So a milestone — a genuinely inline construct — is treated as though it were still block-shaped, the
rejoin is refused, and re-tokenizing the artifact paragraph alone hands the tokenizer leading
inline content, which fabricates the `\p` the user never typed. **Notes have the same hole.** This is
the register's own recurring shape: a transform enumerating node classes where a declared property
was available. It is why fixing "one class" kept surfacing another.

**Fix.** State the gate as the property: the bytes end the split when they do NOT name a
paragraph-kind marker. Character, Note and Milestone all qualify; `Paragraph` does not; `undefined`
(unknown) does not, because the tokenizer's unknown-token default is exactly what makes it block —
that arm must keep behaving as it does today.

**Risk to check, not assume.** The doc comment says notes and milestones "keep their existing
routing rather than gaining a rejoin they never had" — i.e. today's narrowness was deliberate at the
time. Widening it is the right call now (the fabricated `\p` is data the user did not write), but
the note path must be measured, not reasoned about: notes are inline too, so the same rejoin should
be correct there, and if it is not, that is a finding worth reporting rather than special-casing.

Both settle legs read this predicate — the mutating settle and `virtualSettle.utils.ts`'s read-only
recompute — so the fix lands once and covers `getUsj()` automatically. The doc comment says plainly
that a gate only the mutating leg knew about is how the save path once wrote a `\p` the screen never
showed; that stays true.

## 2. Milestones should apply instantly; only DESTRUCTIVE edits wait

**Reported.** Typing `\qt1-s\*` or `\qt1-s |stuff\*` no longer creates the milestone immediately —
it waits for the settle. The owner wants a valid milestone created instantly, and only the
destructive rearrangements (ejecting content, mangling an attribute string) deferred.

**Cause, and it is mine.** The previous round deferred the ejecting rebuild to the settle so bytes
would not move under the caret. The predicate that decides "would this rebuild eject?" is
`milestoneEjectionPending` (`libs/shared/src/converters/usfm/usfmFragmentToUsj.ts`), and it counts
**any string following a milestone** as ejected content:

```ts
return items.slice(index + 1).some((later) => {
  if (typeof later === "string") return true;          // <- too broad
  return later.type === "unmatched" && later.marker === "*";
});
```

A milestone followed by ordinary body text — the common case — matches, so it pends when it should
apply at once.

**Fix.** Narrow the predicate to the actual ejection signature: a milestone followed by content AND
a leftover unmatched `\*`. That is what ejection produces and what body text alone does not.
Equivalently, ask whether the tokenization *differs from what a non-ejecting parse would give*; the
unmatched `\*` is the observable that distinguishes them.

Pin both directions: `\qt1-s\*` + body text applies immediately; `\qt1-s things|sid="x"\*` still
waits for the settle. The existing "moves nothing while the user is still typing" test covers the
second, so the new pin is the first.

## 3. Re-absorption: a fixed attribute string folds back into the milestone

**Ruled by the owner**, with the boundary stated precisely: absorption requires a **trailing
unmatched `\*`**. So

- `\qt1-s\*|who="person"` — no closer — must NOT absorb.
- `\qt1-s\*|who="person"\*` — closer present — MUST absorb, giving `\qt1-s |who="person"\*`.
- Whitespace between the milestone's `\*` and the `|` is tolerated.
- If the milestone already has attributes, **merge, with the body-text attributes overwriting**.
  If it has none, the body-text attributes become exactly its attributes.

That closer requirement also disposes of the corpus risk raised earlier: body text that merely
begins with `|` cannot trigger absorption without an unmatched `\*` after it, so this cannot
silently eat ordinary content.

**Fix.** A lookahead in `scanMilestone`: milestone token, optional whitespace, a `|…` run that
PARSES, then `\*`. Absorb only when the list parses — that is what keeps ejection and absorption
from oscillating, since `\qt1-s\*|who=""\*` does not parse and therefore stays ejected. Pin the
non-oscillation explicitly in both directions; it is the property most likely to break silently.

Also pin the merge semantics (`sid` kept, `who` overwritten) and the whitespace-tolerant form.

## 4. Two clicks to reach the end of a paragraph ending in a footnote

**Reported.** The first click leaves the editor unfocused; the second lands correctly. The owner
wants one click.

**Not yet diagnosed.** The caret-host work from the previous round made the second click work; the
first is a different layer — the editor is not focused yet, so the click that focuses it is consumed
establishing focus rather than placing the caret.

Diagnose before designing. Specifically establish whether this is (a) general to the editor (does a
first click into ordinary text also take two?), or (b) specific to this position. If (a), it is
pre-existing and belongs in its own report rather than being fixed under this heading; if (b), the
guard is likely refusing or relocating a caret that arrives before focus settles.

jsdom has no hit testing, so the click half stays manual either way — but the focus half may well be
testable, and the (a)/(b) question is answerable by hand in one minute.
