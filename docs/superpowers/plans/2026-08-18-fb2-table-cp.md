# Feedback: the row glyph's delete-proofing, and `\cp` folding back onto its chapter

Branch `sv/fb2/table-cp`. Two TJ-approved items against the Standard-view editor. Governing:
`docs/superpowers/specs/2026-08-11-standard-view-invariants.md`. Both landed strict red-green:
each failing test was watched failing for the stated reason against the pre-fix source.

---

## Item 1 — a table row's `\tr ` glyph becomes delete-proof

`OpaqueBlockGuardPlugin` (libs/shared-react) already refused an edit aimed inside an opaque
construct, and TJ's report was that the row's `\tr ` glyph and its NBSP separator could still be
deleted off the screen while the file kept the row. Reproduced first, in a probe harness driving
the real command pipeline: a collapsed caret ON the glyph was already refused, and the two
gestures that were not are the ones the fix addresses.

### The two mechanisms

**A — a selection reaching IN from outside.** The guard's predicate required BOTH ends of the
selection to sit inside the SAME opaque construct. A range anchored at the end of the preceding
paragraph and focused inside the row's glyph therefore passed straight through, and the deletion
gutted the row: `\tr` gone from the screen, the `immutable-table-row` still in the document, and no
settle scope anywhere to reconcile the two (`$settleScopeForNode` returns undefined inside a table,
so nothing re-tokenizes it, ever). Measured on the pre-fix source: `immutable-table " world"` where
`"\tr world"` had been.

The predicate is now "an END of the selection lands inside an opaque construct". A range whose ends
are BOTH outside is deliberately still not the guard's business even when it contains a construct
whole — that is a region replacement, and §4 of the unknown-blocks handoff assigns it to the
structural-deletion rules. The line is exactly "reaching in and stopping inside" (partial gutting,
which nothing repairs) versus "containing it" (a different question with a different owner).

**B — a delete chord never reaches the key filter as typing.** `isEditingKey` disqualifies any
Ctrl/Meta/Alt chord, which is right and load-bearing: Ctrl+C, Ctrl+Z and the marker engine's
Ctrl+Space must all keep working inside a read-only block. But Lexical routes Ctrl/Alt+Backspace
straight to `DELETE_WORD_COMMAND` and Cmd/Ctrl+Backspace to `DELETE_LINE_COMMAND`
(`LexicalEvents`, `$handleKeyDown`), so those never met the guard at all. Rather than loosen the
chord rule — which would break the three chords it exists for — the delete COMMANDS are now
guarded alongside `KEY_DOWN`: `DELETE_CHARACTER_COMMAND`, `DELETE_WORD_COMMAND`,
`DELETE_LINE_COMMAND`. That also covers `DELETE_CHARACTER` dispatched directly, which Lexical does
for a non-Backspace delete-backward.

### A third finding, fixed with them: the refusal tied with the actor

`CUT` and `PASTE` were registered at `COMMAND_PRIORITY_HIGH` — and so are the standard-view cut and
paste handlers in `MarkerEditPlugin`, the ones that actually copy and remove. At equal priority
Lexical decides by registration order, and `MarkerEditPlugin` mounts first, so the cut ran and the
refusal never did. Both now register at `COMMAND_PRIORITY_CRITICAL`: a refusal has to outrank the
actor it refuses, not tie with it. The engine's own CRITICAL cut arm only RECORDS what a cut would
cover and claims nothing, so either order of the two is correct — with no removal, nothing it armed
can be reaped.

`KEY_DOWN` and `CONTROLLED_TEXT_INSERTION` deliberately stay at HIGH: their actors sit at EDITOR
(Lexical's own), so HIGH already wins, and leaving them there keeps the engine's KEY_DOWN
bookkeeping (idle-settle clock, app-placed-caret window, the deletion arms) running exactly as
before a refused key.

### Provenance is untouched

The refusal governs USER gestures only. A refused gesture never reaches the tree, so nothing about
heal-by-provenance changes: machine drift on the row glyph still heals in place through
`$markerNodeTransform`'s heal arm — the row's glyph is an ordinary `MarkerNode`, so it was already
covered, and there is now a pin saying so (invariants §2: machine drift heals, a user edit pends).
No user deletion routes into the heal, because no user deletion arrives at all.

### Tests (`unknownBlockTyping.test.tsx`, +8)

Red first, five of them, each watched failing on the pre-fix source: a selection reaching into the
glyph, one reaching into the separator, a word-delete chord aimed at the glyph, a selection reaching
in that is typed over, and a cut. Plus three that were already green and are pinned anyway: the
collapsed-caret Backspace (the case that already worked), the control — a selection that stays
outside the table still deletes — and the machine-drift heal.

Two harness notes for a later reader:

- The key helper dispatches ONE `KEY_DOWN_COMMAND` and lets Lexical's own listener route it, which
  is what the browser does. An earlier version of the helper also dispatched the delete command
  itself, which double-dispatched and made its return value meaningless; the assertions are on
  document state instead, which is the real contract.
- The word-chord test's pre-fix failure in jsdom is a throw out of the unimplemented
  `domSelection.modify`, not a visible wipe — the same artefact the figure's Backspace pin has.

### Found afterwards: refusing the DELETE left the caret's own arrival unhandled

**2026-08-19 (`2026-08-19-fb4-glyph-caret.md`).** Deletion was refused correctly, but placing a
caret on the row glyph at all threw `Children of root nodes must be elements or decorators` out of
Lexical — on every caret move, from the top-level-element walk that every selection listener starts
with. The cause is not in this item's guard: it is that `ImmutableTableRowNode` declared
`isShadowRoot(): true`, which was harmless while its children were all cells and became illegal the
moment the unknown-blocks track gave the row a `MarkerNode` glyph and an NBSP separator as direct
children. The row has since dropped the claim, as the CELL already had for the identical reason.

The caret could also ENTER the glyph and walk it byte by byte; a read-only construct's glyph is now
a single traversal stop, keyed on this item's own `$opaqueBlockAncestor`.

### What item 1 deliberately leaves open

A selection whose ends are both OUTSIDE a table still guts it into an empty shell (measured:
`immutable-table ""` with the row surviving). That is the region-replacement question §4 assigns
elsewhere, and it is unchanged by this work — recorded here as a cross-group finding rather than
annexed. When table editability lands, `$opaqueBlockAncestor` is still the one predicate where all
of this comes back out.

## Item 2 — a real `\cp` paragraph folds back onto its chapter

### Affordability verdict: affordable, and cheaper than the handoff predicted

The attribute-markers handoff recorded this as needing "a cross-block rebuild scope no current
scope expresses". Measured, the cost is one region rule and one scope rule, because everything else
was already in place:

- **The tokenizer already folds it.** Probed directly: `\c 1 \cp 1` → `pubnumber: "1"`, while
  `\c 1 \cp 1 \nd x\nd*` → chapter plus a first-class `para cp`. Both the fold and the refusal are
  the tokenizer's existing rules (`ATTRIBUTE_MARKERS.cp`, shape `"para"`), pinned at the tokenizer
  already. Nothing in the tokenizer changed, and it stays the single fold authority.
- **The chapter settle scope already exists** and already spans a REGION beyond the chapter's own
  children (the ca-display track's `$chapterAdjacentAttributeChars`).
- **The pend already fires.** `$textNodeTier2Transform`'s chapter arm is written as
  `$isChapterNode($settleScopeForNode(node))` — it asks the scope resolver rather than
  re-deriving adjacency — so widening the resolver made a plain-text edit inside a `\cp` paragraph
  pend with no new trigger code.

So the "cross-block scope" turned out to be the existing chapter region with one more member.

### The fold-back scope shape

`$chapterAdjacentAttributeChars` → **`$chapterAdjacentAttributeNodes`** (`tier2Rebuild.utils.ts`,
exported; the read-only settle must splice the same region). The region after a chapter is:

```
chapter, then zero or more root-level \ca/\cp CHAR spans, then — closing the region — one \cp PARAGRAPH
```

The paragraph CLOSES the region because that is what it does in the file: `\cp` has no closing
marker, so its span runs to the next block boundary and nothing past it can still be the chapter's.

`$settleScopeForNode` gained the matching arm through a new inverse helper,
`$chapterOfAdjacentAttributeNode`. The subtlety is that a `\cp` paragraph, unlike a first-class
`\ca` char, DOES have a scope ancestor — itself — and that scope is the wrong one: re-tokenizing
`\cp 1` alone can only ever produce a `\cp` paragraph, so the chapter has to be in the fragment for
the fold to be expressible at all. The rule is therefore "a scope found DEEPER than the root child
wins; the root child itself can be a chapter's attribute marker":

```ts
if (scope && !scope.is(rootChild)) return scope;
return (rootChild ? $chapterOfAdjacentAttributeNode(rootChild) : undefined) ?? scope;
```

A note nested inside the `\cp` paragraph keeps its own note scope (pinned), because it is the
nearer scope and its own rebuild is the right one.

`$buildChapterFragment` appends the region's bytes as before — a `ParaNode` flows through
`$appendNodesFragment`'s element branch, so its `\cp` glyph, separator and content arrive as
ordinary fragment text — and gained one preserve-or-refuse arm: an adjacent `\cp` paragraph
carrying `unknownAttributes` refuses the whole rebuild, the same rule `$buildParaFragment` applies
to any paragraph. `$rebuildChapter` needed no change beyond the rename: its region drives the
caret-anchor check, the fixed-point signature and the splice already.

The virtual settle mirrors it by construction: `$settledChapter` compares its fixed point over the
same region, and `$settledUsj`'s chapter pass splices `1 + region.length` serialized siblings — so
the folded paragraph vanishes from `getUsj()` exactly as it does from the live tree. That splice is
now the only one that removes a BLOCK slot, which the new equivalence shape pins.

### Timing: the fold lands at the gesture, not at departure

Worth stating plainly because the brief said "settle (departure)". Measured both ways:

- Deleting the `\nd x\nd*` span destroys its glyphs, which the deletion transform routes to Tier 2
  IMMEDIATELY rather than pending — so the fold lands on the keystroke.
- Typing a value into an emptied `\cp` paragraph likewise folds within the gesture's own commit.

Both are strictly EARLIER than the requirement, and this is the precedent the ca-display track set
explicitly for the typed-closer fold. The tests assert the post-departure state regardless —
"settled by the time the caret leaves" is the contract, and a future re-routing of the deletion arm
through the pend ledger must keep them green. The grace-then-departure assertions the first draft
of the test carried were removed as unfounded, not weakened: they asserted a delay the engine does
not promise.

### Tests

`chapterAttributeSettle.test.tsx` (+5, new describe):

- the fold-back: chapter + real `\cp 1 \nd x\nd*`, delete the markup, depart → the paragraph is
  GONE, `pubnumber === "1"`, and the USJ is deep-equal to a reload of `\c 1 \cp 1` (byte-identity
  at the USJ layer, not mere convergence);
- typing a value into an EMPTY `\cp` paragraph folds it — the other half of the round trip;
- guard: a `\cp` paragraph a real paragraph separates from its chapter does NOT fold;
- guard: a `\cp` paragraph that still carries markup does NOT fold (re-tokenizes to itself, refused
  at the fixed point);
- undo restores the paragraph.

`tier2Rebuild.utils.test.tsx` (+4 `$settleScopeForNode` pins) — the unambiguous statement of the
rule, independent of which trigger fires: chapter for a `\cp` paragraph's text and for the
paragraph itself; chapter through an intervening `\ca` char; the paragraph ITSELF when a real
paragraph separates it; the NOTE for a note nested inside it. The two chapter-returning pins were
verified red against the pre-fix resolver; the two guards pass either way, as guards do.

`settledGetUsj.test.tsx` (+1 shape, so +2 tests — equivalence and Tier-2 fixed point): "cp

the edit did not pend at all, so the suite's own vacuity guard

## Deviations, and what was deliberately not done

- **No tokenizer change** (a fixed point) and **no C# change**; the approval gate was never
  approached. The `\cp` fold rules were probed, not edited.
- **No 2SA fixture regeneration.** No serialized shape changed — the guard only refuses commands,
  and the region change alters no adaptor output — confirmed by the corpus suites passing untouched.
- **Item 1's guard change widens `OpaqueBlockGuardPlugin`'s stated limit for one half of it.** §4 of
  the unknown-blocks handoff says a selection spanning a block from outside is not touched; that now
  holds only for a selection that CONTAINS the block, not one that reaches in and stops inside. The
  narrowing is deliberate and is documented at the predicate: reaching in and stopping is a
  guaranteed screen/file divergence with no settle scope to repair it, which is a different question
  from replacing a region.
- **`$chapterAdjacentAttributeChars` was renamed rather than joined by a sibling helper**, so the
  region stays defined in exactly one place for the mutating settle, the read-only settle and the
  scope resolver alike.
- **`CHAPTER_ATTRIBUTE_CHAR_MARKERS` keeps `cp`.** A first-class `cp` CHAR is not a shape the engine
  leaves at rest (a real first-class `cp` is a paragraph), but the chain rule is pure tree geometry
  and the existing pin for it stays green.
- **Scribe untouched** (unmaintained; it mounts neither the guard nor the chapter settle).

## Manual testing worth doing

1. In a running editor, select from the paragraph above a table into the row's `\tr` glyph and press
   Backspace — expect nothing to happen, and the glyph to stay. Then Ctrl+Backspace with the caret
   in the glyph. Then Ctrl+X over the same reaching-in selection. Then confirm Ctrl+C from inside a
   cell still copies and the arrow keys still cross the table.
2. Type markup into a chapter's `\cp` value so it unfolds into a real `\cp` paragraph, then delete
   the markup again — expect the paragraph to disappear and the value to come back as the chapter's
   `\cp` run, without a reload. Then undo, and expect the paragraph back.
3. The same round trip with `getUsj()` read between the steps (the virtual settle), confirming a
   consumer never sees the paragraph the live tree has already folded away.
