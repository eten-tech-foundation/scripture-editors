Branch `sv/co-caret`, off `sv/residual-backlog`. Two items from the reported-bug register's cursor
section — the two that no plan, handoff or follow-up round had ever scoped. Governing:
`docs/superpowers/specs/2026-08-11-standard-view-invariants.md`. Immediately preceding in this file:

TJ's two reports:

1. **Up/Down arrow on a verse marker jumps to the next paragraph.**
2. **Mouse-click after a footnote at paragraph end: the caret disappears; Space then scrolls the

Verdicts: **(1) reproduces, deterministically and headlessly; fixed.** **(2) the underlying gap is

## 1. Up/Down on a verse marker

### What it did

Fixture: two paragraphs, one verse each, standard view (editable markers), so a verse marker is the
glyph text `\v 1 ` the caret walks a character at a time. Caret between the `v` and the number.

| Press | Before | After |
| --- | --- | --- |
| ArrowDown from inside `\v 1 ` | `\v 2 `@5 — **the next paragraph** | unclaimed; the browser moves a line |
| ArrowUp from inside `\v 2 ` | `\v 1 `@5 — the previous paragraph | unclaimed |
| ArrowDown, next verse in the SAME paragraph | `\v 2 `@5 — **sideways along the same line** | unclaimed |

Each press was measured as CLAIMED (`defaultPrevented === true`), which is the assertion the tests
make. jsdom performs no visual-line movement, so "the caret did not move" would pass for the wrong
reason; the pins assert the DECISION — that the press is handed to the browser — not the landing.

### Root cause

`$shouldAttemptVerticalVerseNavigation` asked a NODE-CLASS question:

```ts
if ($isSomeVerseNode(anchorNode)) return true;   // an editable VerseNode is a TextNode subclass
```

That branch can only ever fire in editable-marker mode: `ImmutableVerseNode` is a childless
decorator, so no text point can land on it, and an element point is claimed a line earlier. It was
added by the BCV-display fix (`fc39cc10`) and never had a test, so nothing recorded what it meant
for Standard view — where a verse marker is not a number badge but rendered text in the flow.

The verse jump exists as a **substitute for a position the browser cannot move a visual line from**:
an element point wedged between block nodes, or beside a verse number that hosts no caret of its
own. A caret inside glyph text is not that position. It sits in rendered characters, with rendered
characters on both sides, and the browser's own line movement is correct there — the same answer the
suite already gives for the words a few characters to the right ("cursor in verse text — Lexical
handles, not custom navigation").

`hasVisualLineBeyondCaret` is a partial acknowledgement of the same thing: it yields to the browser
when the caret's verse wraps onto further lines. It cannot help here, because it measures only the
current verse's CONTENT — so it says nothing about a caret inside the marker, and nothing at all
when the verse is one line that the next verse shares.

### The fix

State the rule as the property, not the class:

```ts
function $shouldAttemptVerticalVerseNavigation(selection: RangeSelection): boolean {
  if (selection.anchor.type === "element") return true;
  if (selection.anchor.offset !== 0) return false;
  const previousNode = selection.anchor.getNode().getPreviousSibling();
  return $isSomeVerseNode(previousNode) && $isDecoratorNode(previousNode);
}
```

The retained text case is one screen location with two spellings. Lexical normalizes an element
point to text offset 0 when the next child is a `TextNode`, so offset 0 after a caret-less verse
NUMBER *is* that element point and the jump still owns it. Where the verse marker is glyph text the
question cannot even be asked: Lexical resolves offset 0 of the following text back onto the glyph's
own end (its convention for a text/text seam), which is measured and pinned. So one location cannot
answer twice.

**Deliberately not narrowed further.** The element-point branch keeps every case it had. Narrowing
it is a bigger change to the ratified BCV behaviour and nothing reported points at it.

### Tests

`ArrowNavigationPlugin.test.tsx`, +6 in a new describe under the existing vertical-navigation
group. Five were watched failing on the pre-fix source with `defaultPrevented` true — the defect
stated as an assertion rather than as a landing — and the sixth is the control that the narrowing
did not reach the case it was written for (a caret-less verse number still jumps verse to verse).

## 2. The missing position after a note at a paragraph's end

**Status (2026-08-19, later round, owner-approved): Option A is TAKEN.**
`TrailingNoteCaretGuardPlugin` (shared-react, mounted in `packages/platform/src/editor/Editor.tsx`)
materializes a transient zero-width caret host past a collapsed note that ends its block, and
`EmptyVerseCaretGuardPlugin` was refactored onto the same lifecycle so the two share one
implementation (`transientCaretHost.ts`) rather than one pattern copied twice. All three exclusion
paths the option depended on were re-verified and each covers the new node unchanged; the note under
"Tests" below now describes the ARROW half only, which is unchanged and pinned separately. **That
first cut reached the arrow keys and not the mouse at all; see "Second round" below for the
measurement of why, and the click rule that closes it.**

The pre-existing `TODO` this report points at said: *"we probably need a space character after a
note at the end of a para to allow caret placement after the note. Currently typing will go into the
note."*

### What is established, headlessly

Fixture: standard view, `\p before |note|` where the collapsed note is the paragraph's last child.

- **The only position past the note is the paragraph's own end — an ELEMENT point, with no text
  node.** The note is the last child; nothing follows it.
- **The forward arrow rests the caret exactly there** and claims the press. It is the visible-stop
  normalizer's doing: a collapsed note is a visible atom, crossed whole, and the landing
  canonicalizes to the element point past it.
- **One backward press recovers**, landing at the end of the text before the note. This matches the
  report's "Arrow-left works" precisely.
- **Typing there is correct in the MODEL** — a new text node as the paragraph's last child, after
  the note, not inside it. Only the rendered caret is missing.
- **A caret placed inside the collapsed note's hidden content is NOT recovered by one backward
  press**: it walks the hidden bytes one character at a time, invisibly.

That last point is the discriminator. If the click landed inside the note's hidden content, one
ArrowLeft would appear to do nothing; TJ reports it works. So the click resolves to the paragraph's
end element point — the position with no text node — and everything else in the report follows: no
rendered text at that spot means no insertion point drawn, and a keypress with no insertion point is
the page's rather than the editor's, which is why Space scrolls.

### What jsdom cannot establish, and is not claimed here

jsdom implements no layout and no hit testing — there is no `caretRangeFromPoint` — so **which DOM
position a real click produces cannot be measured here at all**, and neither can whether a browser
paints a caret at the element point. The chain above is an inference from the reported symptoms plus
what IS measured, not a measurement of the click. A real-browser check is the way to close it; the
manual steps below are written for that.

### The contained half, taken

Crossing the note from the element point BEFORE it went **into** the note: measured landing, the end
of the note's hidden closing glyph. That is the `selectEnd()` fallback the TODO sat on, and it is
strictly worse than the unhosted point outside — a collapsed note's content is hidden, so the caret
is invisible there AND typing silently edits the note body instead of the paragraph. Wrong bytes
change; that is the failure Invariant I exists to forbid, and an unpainted caret that one backward
press recovers is not.

So both `selectEnd()` fallbacks now land PAST the note, agreeing with where crossing it from the
text already lands. An EXPANDED note's own end is rendered and stays a legitimate resting place, so
that case is untouched.

This does not depend on which way the visibility question below is answered, and does not foreclose
any of them.

### The design question: options, costs, recommendation

**A. A transient caret host after a trailing note.** Insert a zero-width-space text node after the
note when the caret comes to rest past it, select into it, remove it when the caret leaves or on
blur, strip it the moment real text is typed.

- The pattern is already ratified and shipped here: `EmptyVerseCaretGuardPlugin` does exactly this
  for a verse whose text has been fully deleted, for the identical reason (a childless decorator
  leaves only an element point, which the browser draws no caret at).
- Every exclusion path a transient host needs **already exists and already covers this node**:
  `CURSOR_CHANGE_TAG` keeps the mutation out of save emission, `editor-delta.adaptor.ts` skips a
  bare-placeholder text node so OT/delta offsets are unaffected, and the USJ serializer drops it.
  This is the single biggest reason to prefer A: the expensive part is built.
- Cost: one plugin (~120 lines) plus tests, mounted in `packages/platform/src/editor/Editor.tsx`.
  Interaction surface to decide deliberately rather than discover: the trailing-space transform and
  `$addTrailingSpace` (the host is a text node in a paragraph they act on), marker settle waking on
  the dirtied paragraph, and the forward-arrow note branches, which would now find a next sibling
  and stop on it — the desired outcome, but it should be chosen, not inherited.
- It is the only option that supplies the position the TODO says is missing, so it is also the only
  one under which the user can type after a footnote that ends a paragraph.
- It does not depend on which of the two possible click landings is real: with a rendered text
  position at the end of the line, a hit test has somewhere correct to resolve to.

**B. Correct the click, the way the paragraph-prefix guard already corrects one.**
`ParaMarkerPrefixCursorGuardPlugin` answers `CLICK_COMMAND` and moves a caret that came to rest
somewhere no caret may be, in the same update cycle. The same rule could send a click that resolved
past a trailing note back to the end of the text before it.

- Cost: ~20 lines in an existing plugin, plus tests. No new node, no serialization surface, no delta
  surface, nothing transient. By far the cheapest.
- It fixes the reported symptom — the caret is always visible, Space always types.
- It makes "type after a footnote at a paragraph's end" permanently unreachable. That is the status
  quo today, so it is not a regression; but ratifying it is a product decision, not a caret fix.
- Compatible with A landing later: A would claim the position before B's rule saw it.

**C. Render a caret-hosting box for the note in the DOM only.** Rejected: non-Lexical DOM inside the
editor fights the reconciler, and what the browser needs is a real text node — which is A.

**D. A real trailing space after the note.** Tempting, because the writer contract makes a trailing
space at a paragraph's end free in the FILE (§3 rule 3: the newline before a block marker eats it).
Rejected anyway: it is still a fabricated byte in the USJ the host round-trips, it is precisely the
`$addTrailingSpace` fabrication §7 removed, and it would turn the fixed-point test red.

**E. Record it and stop.** Zero cost; the caret keeps vanishing where a footnote ends a paragraph,
which is common.

**Recommendation: A**, with B as the stop-gap if a second transient-node site is unwelcome. A is the
only answer that closes the gap rather than routing around it, and the apparatus it needs is already
built and already used for an identical purpose one node class over.

### Tests

`ArrowNavigationPlugin.test.tsx`, +6 in a new describe. Five are CHARACTERIZATION — they record the

the file. Whichever way the gap is closed, they go red and name what changed. The sixth is the

### Second round: the click never reached the guard at all

**Owner's verdict on the first attempt: "still doesn't work at all. Still scrolls." Arrow keys reach
the position; clicking does not.** Confirmed, and the cause is sharper than the guess that a click
"cannot resolve to a position with no text node".

**Measured**, by rendering the standard-view DOM of `\p before |collapsed note|` and asking Lexical's
own DOM-position resolver (`$createRangeSelectionFromDom`) what each position a hit test could
produce becomes:

| DOM position at the end of that line | Lexical resolves it to |
| --- | --- |
| `(paragraph, childCount)` — the paragraph's own end | a TEXT point at the end of the note's hidden `\f*` closing glyph |
| `(note span, 2)` — just past the caller, where a click to its right lands | a TEXT point in the note's hidden NBSP separator |
| `(note span, childCount)` | the hidden closing glyph again |
| `(note span, 1)` — on the caller | an ELEMENT point ON the note |
| inside the caller decorator | **no selection at all** — `$getSelection()` is `null` |

**Not one of them is the boundary past the note.** Lexical descends an element point at a block's end
into its last child, so the paragraph's own end lands *inside* the note. The rule the first round
shipped watched only that boundary — the position a forward arrow press produces — so it was inert
on every click, which is exactly "arrows work, clicking does nothing". The `null` row also explains
"Space scrolls": with no selection there is no caret in the editor and the keypress is the page's.

**Taken: the click gets its own question.** `$trailingNoteCaretAnchor` (selection-change, the arrow
landing) is unchanged in meaning. `$trailingNoteUnderClick` answers `CLICK_COMMAND` from the caret
when the click produced one and from the DOM selection when it did not — the same fallback, for the
same reason, that `$guardCursorAtGutterMarker` makes to the click's target. Both drive one repair,
now stated once in `transientCaretHost.ts`: *put the caret at the boundary past this node, and give
that boundary a host if nothing there renders one.*

**Rejected: making the host exist whenever the shape does.** It would give a hit test a real text
position, and the measurement above says `(paragraph, childCount)` does then resolve to the host. But
a permanent placeholder is in the clipboard path, which has no placeholder awareness (the existing
"a range selection removes the host" test exists precisely because of that), and in every consumer
that counts characters. The transient design exists to avoid exactly that, and the click still has to
be answered for the landings that resolve into the note rather than past it.

**Rejected: evicting any caret that comes to rest inside a collapsed note.** Tried, and the platform
suite refuted it: the marker menu deliberately puts a caret inside a collapsed footnote to insert a
char marker into it. A caret in hidden content is not wrong in general — only a caret the user put
there by pointing at blank line-end space is, and that is a property of the CLICK, not of the caret.

**The second half of the report — a click between the paragraphs landing before the next paragraph's
`\` — is pre-existing, not a regression.** The guard mutates nothing until the caret arrives at a
position the measurement above shows no click can produce, so it could not have altered where any
click landed. A click at a paragraph's start in standard view resting before the marker glyph is
ratified behavior: `$guardCursorAtParaStart` deliberately does not correct an EDITABLE marker, which
is a `TextNode` the user clicks into on purpose.

### What is pinned, and what a browser still has to answer

Pinned headlessly: the resolution table above, as a characterization test; that a click from each of
those positions leaves the caret in a host past the note and never in the note; that a click Lexical
resolved to no caret is repaired from the DOM selection; that an ordinary click is left alone; that a
caret placed inside a note by anything other than a click is left alone; that a host already at the
boundary is reused rather than stacked; and, through the production adaptors, that the arrival leaves
the loaded USJ a byte-identical fixed point and that typing there lands after the note in the saved
USJ.

Not pinnable here, and unchanged from the first round: **which DOM position a real click at given
coordinates produces**, and **whether a browser paints a caret in the host**. jsdom has no layout, no
hit testing and no `caretRangeFromPoint`. The tests supply the DOM position; the browser's choice of
it is the manual check below.

## Deliberately not done

- **No node change and no serialization change** — still true after Option A landed: the caret host
  is an ordinary `TextNode` carrying the existing cursor-placeholder character, and every exclusion
  it needs was already in place.
- **No C# change**; the approval gate was never approached. **No tokenizer change.**
- **The element-point branch of vertical verse navigation is untouched**, and so is
  `hasVisualLineBeyondCaret` — its verse-content bound is a real limitation, but the fix above
  removes the case that made it matter.
- **The unrelated TODO at the top of the plugin** (Up/Down before an empty verse number in an
  otherwise empty paragraph) is left as it was; it is a different report.
- **Scribe untouched** (unmaintained).
- **No fixture regeneration** — no serialized shape changed.

## Cross-group findings

- **A node-class test inside a caret rule ages badly.** `$isSomeVerseNode(anchorNode)` was written
  when a verse marker was a decorator; the moment one view rendered it as text, the same line meant
  something entirely different. The rules that survive in this file are the ones phrased as
  properties — "hosts no caret of its own", "renders nothing", "is at its block's edge".
- **jsdom can measure the DECISION even where it cannot measure the movement.** Asserting
  `defaultPrevented` turns "the browser should own this press" into a real assertion instead of a
  caret that stood still for unknown reasons. `pressKey` now returns its event for this.
- **"Invisible caret" has at least two distinct causes here now.** fb5 found `contenteditable=false`
  making a subtree caret-hostile; this one is an element point with no text node to draw in. Both
  end with a caret Lexical is happy with and the browser will not paint, and neither is visible from
  the tree alone.
- **A caret lost OUTSIDE a hidden construct is much better than one lost inside it.** Outside, one
  backward press recovers and nothing has changed; inside, typing edits bytes the user cannot see.
  Where a rule has to choose a wrong-ish landing, that is the direction.

## Please test by hand

1. **Put the caret inside a verse marker's glyph (between the `\` and the `v`, say) in a verse whose
   text wraps onto several lines, and press Down.** Expect the caret to move down ONE visual line
   within the same verse — not to jump to the next verse or the next paragraph. Press Up from the
   second line and expect to come back. This is the reported bug.
2. **Same, in a paragraph holding several verses on one line** (`\v 1 a \v 2 b \v 3 c`). Down and Up
   must not slide the caret sideways along the line.
3. **Confirm the verse jump still works where it always did**: caret at the boundary right after a
   verse NUMBER in a view where the number is a badge rather than glyph text (non-editable markers),
   Down moves to the next verse and the reference display follows.
4. **A footnote at the very end of a paragraph: click to the right of the caller**, in the blank
   space at the end of that line. Expect a visible caret at the end of the line, past the caller,
   and Space to type a space there rather than scroll the page. Then type a word: it must appear
   after the footnote, in the paragraph, and the footnote's own text must be unchanged (open the
   note and check). This is the measurement no headless test can make.
   - **Then click somewhere else and come back and click again**, twice in a row at the same spot.
     The caret must land the same way both times, and no stray character may accumulate at the end
     of the paragraph — save and reopen to confirm the paragraph ends exactly where it did.
   - **Also click directly ON the footnote caller.** Whatever the caller's own click does should
     still happen; if a caret appears as well it belongs past the caller, never inside the note.
   - **And click in the blank space at the end of an ordinary line** (no footnote) in the same
     document, to confirm that still puts the caret at the end of that line.
5. **Same footnote, arrow across it**: from the end of the text before it press Right once, then
   type. Expect the typed character AFTER the footnote, in the paragraph — never inside the note.
   Then press Left and expect to land at the end of the text before the note.
6. **A footnote at the end of the LAST paragraph in the chapter**: press Right past it repeatedly.
   The caret must not disappear into the note, and nothing may be typed into the note body.
